## 一、核心问题

**一个文档应该放在哪个目录？**

当文档内容跨越多个领域时，如何决策归属？

---

## 二、分类决策树

### 2.1 第一步：判断内容性质

```
这个文档主要回答什么问题？

┌─────────────────┬────────────────────────────────────────────┐
│ 问题类型        │ 归属目录                                    │
├─────────────────┼────────────────────────────────────────────┤
│ "为什么这样做"  │ architecture/decisions/ (ADR)              │
│ (决策背景)      │                                            │
├─────────────────┼────────────────────────────────────────────┤
│ "规则是什么"    │ business/                                  │
│ (业务规则)      │                                            │
├─────────────────┼────────────────────────────────────────────┤
│ "怎么实现"      │ engineering/modules/ 或 engineering/api/   │
│ (技术实现)      │                                            │
├─────────────────┼────────────────────────────────────────────┤
│ "怎么开发"      │ engineering/development/                   │
│ (开发规范)      │                                            │
├─────────────────┼────────────────────────────────────────────┤
│ "用户怎么用"    │ product/features/ 或 public/manual/        │
│ (功能说明)      │                                            │
├─────────────────┼────────────────────────────────────────────┤
│ "这是什么"      │ project/ (术语、概念)                      │
│ (基础定义)      │                                            │
└─────────────────┴────────────────────────────────────────────┘
```

### 2.2 第二步：判断主要读者

```
谁是这个文档的主要读者？

┌─────────────────┬────────────────────────────────────────────┐
│ 读者            │ 归属目录                                    │
├─────────────────┼────────────────────────────────────────────┤
│ 开发者          │ engineering/                               │
├─────────────────┼────────────────────────────────────────────┤
│ 产品/业务       │ product/ 或 business/                      │
├─────────────────┼────────────────────────────────────────────┤
│ 运营/市场       │ growth/                                    │
├─────────────────┼────────────────────────────────────────────┤
│ 终端用户        │ public/                                    │
├─────────────────┼────────────────────────────────────────────┤
│ 所有人/AI       │ project/ (入口级文档)                      │
└─────────────────┴────────────────────────────────────────────┘
```

### 2.3 第三步：处理跨领域内容

当内容跨越多个领域时，**以决策权归属为准**：

```
决策权在谁手上？

┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  业务/产品决定的 ──────────────→ business/                  │
│  例：Tier 权限、定价、积分规则                              │
│                                                             │
│  技术/架构决定的 ──────────────→ engineering/               │
│  例：数据库设计、API 设计、缓存策略                         │
│                                                             │
│  两者都涉及 ───────────────────→ 拆分文档                   │
│  例：Feature Flag                                           │
│       - 评估优先级（业务规则）→ business/                   │
│       - 实现方式（技术细节）→ engineering/                  │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 三、各目录的收录原则

### 3.1 `01-project/` - 项目基础

| 收录 | 不收录 |
|------|--------|
| 项目简介、愿景 | 具体功能说明 |
| 技术栈概览 | 详细技术实现 |
| 术语表、核心概念 | 业务规则细节 |
| 项目级决策日志 | 模块级决策 |

**判断标准**：新人或 AI 需要首先了解的基础信息

### 3.2 `02-product/` - 产品规格

| 收录 | 不收录 |
|------|--------|
| 功能需求（做什么） | 技术实现（怎么做） |
| 用户故事 | 数据库设计 |
| 页面设计 | API 定义 |
| 交互流程 | 代码结构 |

**判断标准**：产品经理关心的内容

### 3.3 `03-design/` - 设计系统

| 收录 | 不收录 |
|------|--------|
| 颜色、字体、间距 Token | 组件代码实现 |
| 组件视觉规范 | 业务逻辑 |
| 设计模式、布局规则 | API 设计 |
| 品牌规范 | 功能规格 |

**判断标准**：设计师和前端开发共同遵守的视觉规范

### 3.4 `04-engineering/` - 技术实现

| 子目录 | 收录 | 不收录 |
|--------|------|--------|
| `architecture/` | 系统架构、技术选型、ADR | 业务规则 |
| `modules/` | 模块技术设计、代码结构 | 功能需求 |
| `api/` | API 定义、错误码、协议 | 业务逻辑 |
| `development/` | 开发规范、测试规范、日志规范 | 功能说明 |
| `data/` | 数据库 Schema、实体定义 | 业务规则 |

**判断标准**：开发者实现功能时需要的技术文档

### 3.5 `05-business/` - 业务规则

| 收录 | 不收录 |
|------|--------|
| 业务规则定义 | 技术实现细节 |
| Tier 权限、定价、积分规则 | 代码示例 |
| 用户生命周期、订阅规则 | 数据库设计 |
| 权益系统规则 | API 定义 |

**判断标准**：业务/产品决定的规则，开发者必须遵守

**重要区分**：
- "Tier t2 有 100 月度积分" → **business/** (业务规则)
- "积分存储在 credit_transactions 表" → **engineering/** (技术实现)

### 3.6 `06-growth/` - 运营增长

| 收录 | 不收录 |
|------|--------|
| 获客、留存、变现策略 | 技术实现 |
| SEO、内容策略 | 具体代码 |
| 用户支持策略 | 业务规则定义 |

**判断标准**：运营/市场关心的增长策略

### 3.7 `07-analytics/` - 数据分析

| 收录 | 不收录 |
|------|--------|
| 指标定义、埋点规范 | 埋点代码实现 |
| 看板说明 | 数据库设计 |
| 分析报告模板 | ETL 实现 |

**判断标准**：数据分析需要的定义和规范

### 3.8 `08-operations/` - 运维

| 收录 | 不收录 |
|------|--------|
| 部署流程、环境配置 | 代码架构 |
| 监控、告警规则 | 业务规则 |
| 故障处理流程 | 功能说明 |

**判断标准**：运维/DevOps 需要的操作文档

### 3.9 `09-compliance/` - 合规

| 收录 | 不收录 |
|------|--------|
| 法务要求、数据合规 | 技术实现 |
| GDPR、COPPA 要求 | 代码示例 |

**判断标准**：法务/合规相关的要求

### 3.10 `10-governance/` - 文档治理

| 收录 | 不收录 |
|------|--------|
| 文档模板 | 业务内容 |
| 命名规范、分类原则 | 技术文档 |
| 同步策略 | 功能说明 |

**判断标准**：关于"如何写文档"的元文档

## 四、边界案例处理

### 4.1 案例：Feature Flag 系统

```
Feature Flag 文档涉及：
1. 评估优先级规则（Kill Switch > Override > Tier > Flag）
2. Flag 类型定义（Boolean/Percentage/Experiment）
3. 技术实现（数据库表、评估代码）

分析：
- 评估优先级 → 业务决定 → business/entitlement/policy-rules.md ✓
- Flag 类型 → 业务定义 → business/entitlement/policy-rules.md
- 技术实现 → 开发需要 → engineering/modules/platform/feature-flags.md

结论：拆分为两个文档
```

### 4.2 案例：错误码定义

```
错误码涉及：
1. 错误码格式（AUTH_xxx, BIZ_xxx）
2. HTTP 状态码对应
3. 前端处理建议

分析：
- 主要读者是开发者
- 主要用于 API 调用
- 是技术约定，不是业务规则

结论：engineering/api/error-codes.md ✓
```

### 4.3 案例：Tier 权限矩阵

```
权限矩阵涉及：
1. 各 Tier 能用什么功能
2. 功能配额（项目数、存储空间）

分析：
- 这是业务决定的规则
- 产品、客服、开发都需要查阅
- 不涉及技术实现

结论：business/tier-system/feature-matrix.md
      或合并到 business/entitlement/permission-matrix.md
```

### 4.4 案例：术语表

```
术语表涉及：
- 产品术语、教育术语、业务术语、技术术语

分析：
- 所有人都需要（新人入门、AI 上下文）
- 是项目级基础信息
- 不属于任何具体领域

结论：project/glossary.md ✓
```

## 五、禁止事项

1. **禁止创建"杂项"目录**
   - ❌ `misc/`, `others/`, `reference/`
   - 如果无法归类，说明分类原则需要完善

2. **禁止同一内容放多处**
   - 选择一个主位置，其他地方用链接引用

3. **禁止目录名过于宽泛**
   - ❌ `standards/` (什么的标准？)
   - ✅ `development/testing-guide.md` (开发测试规范)

4. **禁止按文件类型分类**
   - ❌ `guides/`, `specs/`, `references/`
   - ✅ 按内容领域分类
