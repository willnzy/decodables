# Part 1: 归属决策

> **核心问题**：一个文档应该放在哪个目录？

---

## 1.1 三步决策树

### 第一步：判断内容性质

```
这个文档主要回答什么问题？

┌─────────────────┬────────────────────────────────────────────┐
│ 问题类型        │ 归属目录                                    │
├─────────────────┼────────────────────────────────────────────┤
│ "为什么这样做"  │ architecture/decisions/ (ADR)              │
│ (决策背景)      │                                            │
├─────────────────┼────────────────────────────────────────────┤
│ "规则是什么"    │ business/                                  │
│ (业务规则)      │                                            │
├─────────────────┼────────────────────────────────────────────┤
│ "怎么实现"      │ engineering/modules/ 或 engineering/api/   │
│ (技术实现)      │                                            │
├─────────────────┼────────────────────────────────────────────┤
│ "怎么开发"      │ engineering/development/                   │
│ (开发规范)      │                                            │
├─────────────────┼────────────────────────────────────────────┤
│ "用户怎么用"    │ product/features/ 或 public/manual/        │
│ (功能说明)      │                                            │
├─────────────────┼────────────────────────────────────────────┤
│ "这是什么"      │ project/ (术语、概念)                      │
│ (基础定义)      │                                            │
└─────────────────┴────────────────────────────────────────────┘
```

### 第二步：判断主要读者

```
谁是这个文档的主要读者？

┌─────────────────┬────────────────────────────────────────────┐
│ 读者            │ 归属目录                                    │
├─────────────────┼────────────────────────────────────────────┤
│ 开发者          │ engineering/                               │
├─────────────────┼────────────────────────────────────────────┤
│ 产品/业务       │ product/ 或 business/                      │
├─────────────────┼────────────────────────────────────────────┤
│ 运营/市场       │ growth/                                    │
├─────────────────┼────────────────────────────────────────────┤
│ 终端用户        │ public/                                    │
├─────────────────┼────────────────────────────────────────────┤
│ 所有人/AI       │ project/ (入口级文档)                      │
└─────────────────┴────────────────────────────────────────────┘
```

### 第三步：处理跨领域内容

当内容跨越多个领域时，**以决策权归属为准**：

```
决策权在谁手上？

┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  业务/产品决定的 ──────────────→ business/                  │
│  例：Tier 权限、定价、积分规则                              │
│                                                             │
│  技术/架构决定的 ──────────────→ engineering/               │
│  例：数据库设计、API 设计、缓存策略                         │
│                                                             │
│  两者都涉及 ───────────────────→ 拆分文档                   │
│  例：Feature Flag                                           │
│       - 评估优先级（业务规则）→ business/                   │
│       - 实现方式（技术细节）→ engineering/                  │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 1.2 各目录收录原则

### `01-project/` - 项目基础

| 收录 | 不收录 |
|------|--------|
| 项目简介、愿景 | 具体功能说明 |
| 技术栈概览 | 详细技术实现 |
| 术语表、核心概念 | 业务规则细节 |
| 项目级决策日志 | 模块级决策 |

**判断标准**：新人或 AI 需要首先了解的基础信息

### `02-product/` - 产品规格

| 收录 | 不收录 |
|------|--------|
| 功能需求（做什么） | 技术实现（怎么做） |
| 用户故事 | 数据库设计 |
| 页面设计 | API 定义 |
| 交互流程 | 代码结构 |

**判断标准**：产品经理关心的内容

### `03-design/` - 设计系统

| 收录 | 不收录 |
|------|--------|
| 颜色、字体、间距 Token | 组件代码实现 |
| 组件视觉规范 | 业务逻辑 |
| 设计模式、布局规则 | API 设计 |
| 品牌规范 | 功能规格 |

**判断标准**：设计师和前端开发共同遵守的视觉规范

### `04-engineering/` - 技术实现

| 子目录 | 收录 | 不收录 |
|--------|------|--------|
| `architecture/` | 系统架构、技术选型、ADR | 业务规则 |
| `modules/` | 模块技术设计、代码结构 | 功能需求 |
| `api/` | API 定义、错误码、协议 | 业务逻辑 |
| `development/` | 开发规范、测试规范、日志规范 | 功能说明 |
| `data/` | 数据库 Schema、实体定义 | 业务规则 |

**判断标准**：开发者实现功能时需要的技术文档

### `05-business/` - 业务规则

| 收录 | 不收录 |
|------|--------|
| 业务规则定义 | 技术实现细节 |
| Tier 权限、定价、积分规则 | 代码示例 |
| 用户生命周期、订阅规则 | 数据库设计 |
| 权益系统规则 | API 定义 |

**判断标准**：业务/产品决定的规则，开发者必须遵守

**重要区分**：
- "Tier t2 有 100 月度积分" → **business/** (业务规则)
- "积分存储在 credit_transactions 表" → **engineering/** (技术实现)

### `06-growth/` - 运营增长

| 收录 | 不收录 |
|------|--------|
| 获客、留存、变现策略 | 技术实现 |
| SEO、内容策略 | 具体代码 |
| 用户支持策略 | 业务规则定义 |

**判断标准**：运营/市场关心的增长策略

### `07-analytics/` - 数据分析

| 收录 | 不收录 |
|------|--------|
| 指标定义、埋点规范 | 埋点代码实现 |
| 看板说明 | 数据库设计 |
| 分析报告模板 | ETL 实现 |

**判断标准**：数据分析需要的定义和规范

### `08-operations/` - 运维

| 收录 | 不收录 |
|------|--------|
| 部署流程、环境配置 | 代码架构 |
| 监控、告警规则 | 业务规则 |
| 故障处理流程 | 功能说明 |

**判断标准**：运维/DevOps 需要的操作文档

### `09-compliance/` - 合规

| 收录 | 不收录 |
|------|--------|
| 法务要求、数据合规 | 技术实现 |
| GDPR、COPPA 要求 | 代码示例 |

**判断标准**：法务/合规相关的要求

### `10-governance/` - 文档治理

| 收录 | 不收录 |
|------|--------|
| 文档模板 | 业务内容 |
| 命名规范、分类原则 | 技术文档 |
| 同步策略 | 功能说明 |

**判断标准**：关于"如何写文档"的元文档

## 1.3 同步范围判断原则

### 判断流程

```
这个文档的内容，前后端都需要了解吗？

┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  只有后端关心                                               │
│  例：数据库设计、Repository 实现、Webhook 处理              │
│  → [backend]                                                │
│                                                             │
│  只有前端关心                                               │
│  例：组件实现、Canvas 架构、Store 设计                      │
│  → [frontend]                                               │
│                                                             │
│  前后端都需要了解                                           │
│  例：业务规则、API 定义、错误码、权限矩阵                   │
│  → [fullstack]                                              │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 判断标准

| 同步范围 | 判断标准 | 示例 |
|----------|----------|------|
| `[fullstack]` | 前后端都需要遵守或了解 | 业务规则、API 契约、错误码 |
| `[backend]` | 仅后端实现细节 | Repository、数据库迁移、Webhook |
| `[frontend]` | 仅前端实现细节 | 组件、Store、Canvas |

### 边界案例

| 文档 | 判断 | 原因 |
|------|------|------|
| `billing-lifecycle.md` | fullstack | 前端展示状态，后端处理逻辑，两边都要懂 |
| `canvas-architecture.md` | frontend | 纯前端技术，后端不需要了解 |
| `stripe-webhook.md` | backend | 纯后端处理，前端不涉及 |
| `error-codes.md` | fullstack | 前端需要处理错误，后端需要返回错误 |

## 1.4 粒度判断原则

### 何时拆分

```
一个文档是否应该拆分成多个？

┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  ✅ 应该拆分的情况：                                        │
│                                                             │
│  1. 超过 500 行，且包含多个独立主题                         │
│     例：billing.md → billing-lifecycle.md + credits.md      │
│                                                             │
│  2. 不同部分的读者不同                                      │
│     例：auth.md → auth-flow.md (产品) + auth-impl.md (开发) │
│                                                             │
│  3. 更新频率差异大                                          │
│     例：稳定的规则 vs 频繁变化的配置                        │
│                                                             │
│  4. 跨越多个目录的归属                                      │
│     例：feature-flag → policy-rules.md + feature-flags.md   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 何时合并

```
多个文档是否应该合并成一个？

┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  ✅ 应该合并的情况：                                        │
│                                                             │
│  1. 内容高度相关，分开后需要频繁跳转                        │
│     例：tier-permissions.md + tier-quotas.md → tier.md      │
│                                                             │
│  2. 每个文档都很短（< 100 行）                              │
│     例：多个小配置文档 → 一个配置汇总                       │
│                                                             │
│  3. 总是一起查阅                                            │
│     例：API 请求 + 响应 + 错误码 → 一个 API 文档            │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 粒度参考

| 文档类型 | 建议粒度 | 说明 |
|----------|----------|------|
| 模块架构 | 一个模块一个文档 | `billing/architecture.md` |
| API 文档 | 按功能域划分 | `user-endpoints.md`, `admin-endpoints.md` |
| 业务规则 | 按主题划分 | `tier-system.md`, `credits-system.md` |
| 功能规格 | 一个功能一个文档 | `editor.md`, `dashboard.md` |

## 1.5 与代码路径的对应关系

### 对应原则

```
文档路径是否应该与代码路径对应？

┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  模块文档 → 对应代码目录                                    │
│                                                             │
│  代码: domains/billing/                                     │
│  文档: engineering/modules/billing/                         │
│                                                             │
│  代码: domains/auth/                                        │
│  文档: engineering/modules/auth/                            │
│                                                             │
│  ─────────────────────────────────────────────────────────  │
│                                                             │
│  业务规则 → 按业务概念组织，不对应代码                      │
│                                                             │
│  文档: business/tier-system/                                │
│  代码: 分散在 domains/billing/, domains/identity/           │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 对应表

| 代码目录 | 文档目录 | 说明 |
|----------|----------|------|
| `domains/billing/` | `engineering/modules/billing/` | 模块技术文档 |
| `domains/billing/` | `business/credits-system/` | 业务规则文档 |
| `api/routers/` | `engineering/api/` | API 文档 |
| `@business/stores/` | `engineering/modules/*/` | 前端模块文档 |

## 1.6 边界案例处理

### 案例 1：Feature Flag 系统

```
Feature Flag 文档涉及：
1. 评估优先级规则（Kill Switch > Override > Tier > Flag）
2. Flag 类型定义（Boolean/Percentage/Experiment）
3. 技术实现（数据库表、评估代码）

分析：
- 评估优先级 → 业务决定 → business/entitlement/policy-rules.md
- 技术实现 → 开发需要 → engineering/modules/platform/feature-flags.md

结论：拆分为两个文档
```

### 案例 2：错误码定义

```
错误码涉及：
1. 错误码格式（AUTH_xxx, BIZ_xxx）
2. HTTP 状态码对应
3. 前端处理建议

分析：
- 主要读者是开发者
- 主要用于 API 调用
- 是技术约定，不是业务规则

结论：engineering/api/error-codes.md
同步范围：[fullstack]（前端需要处理错误）
```

### 案例 3：Tier 权限矩阵

```
权限矩阵涉及：
1. 各 Tier 能用什么功能
2. 功能配额（项目数、存储空间）

分析：
- 这是业务决定的规则
- 产品、客服、开发都需要查阅
- 不涉及技术实现

结论：business/tier-system/feature-matrix.md
同步范围：[fullstack]
```

### 案例 4：术语表

```
术语表涉及：
- 产品术语、教育术语、业务术语、技术术语

分析：
- 所有人都需要（新人入门、AI 上下文）
- 是项目级基础信息
- 不属于任何具体领域

结论：project/glossary.md
同步范围：[fullstack]
```

## 1.7 禁止事项

1. **禁止创建"杂项"目录**
   - ❌ `misc/`, `others/`, `reference/`, `standards/`
   - 如果无法归类，说明分类原则需要完善

2. **禁止同一内容放多处**
   - 选择一个主位置，其他地方用链接引用

3. **禁止目录名过于宽泛**
   - ❌ `standards/` (什么的标准？)
   - ✅ `development/testing-guide.md` (开发测试规范)

4. **禁止按文件类型分类**
   - ❌ `guides/`, `specs/`, `references/`
   - ✅ 按内容领域分类

# Part 2: 内容管理

> **核心问题**：文档内容从哪里来？如何保持准确？

---

## 2.1 内容来源优先级

```
┌─────────────────────────────────────────────────────────────────────┐
│                     内容来源优先级（从高到低）                         │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  1️⃣ 代码实际状态（Code as Single Source of Truth）                  │
│     - 从代码结构、逻辑、注释中提取                                    │
│     - 这是唯一的事实来源                                             │
│                                                                     │
│  2️⃣ v1/v2 文档（参考验证）                                          │
│     - 与代码对照后，一致的内容可采用                                  │
│     - 不一致时以代码为准，标注差异                                    │
│                                                                     │
│  3️⃣ 业务规则确认（人工确认）                                         │
│     - 代码和文档都无法确定时，需要人工确认                            │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

---

## 2.2 内容分类及处理规则

| 类型 | 识别特征 | 处理规则 | 存放位置 |
|------|----------|----------|----------|
| **A. 当前实现** | 代码中已实现的功能/逻辑 | 从代码提取，写入正式文档 | `internal/` 对应目录 |
| **B. 已验证规则** | v1/v2 内容与代码一致 | 采用文档内容，标注"已验证" | `internal/` 对应目录 |
| **C. 文档过时** | v1/v2 内容与代码不符 | 以代码为准，记录差异原因 | `internal/` + 差异说明 |
| **D. 代码未实现** | v1/v2 有设计但代码未实现 | 归类为"待实现"规划 | `internal/.../planned/` |
| **E. 方案分析** | 曾经的技术选型对比 | 保留到 ADR（决策记录） | `architecture/decisions/` |
| **F. 重构规划** | 未来要做的重构设计 | 保留完整设计 | `internal/.../planned/` |
| **G. 已完成任务** | 审计报告、执行计划等 | 归档或删除 | `archive/` 或删除 |
| **H. 临时内容** | 分析过程、临时笔记 | 用完删除或同步后删除 | `tmp/` |

## 2.3 状态标注

### 文档状态

| 状态 | 标记 | 含义 |
|------|------|------|
| 已验证 | 🟢 | 内容与代码一致，可信赖 |
| 待验证 | 🟡 | 内容待核实，可能过时 |
| 已过时 | 🔴 | 内容与代码不符，需更新 |

### 元数据模板

```markdown
# 文档标题

> **版本**: x.y.z
> **创建日期**: YYYY-MM-DD
> **最后更新**: YYYY-MM-DD
> **状态**: 🟢 已验证 | 🟡 待验证 | 🔴 已过时
> **同步范围**: [fullstack] | [backend] | [frontend]
> **数据来源**: path/to/code（如适用）

---

正文内容...
```

## 2.4 更新触发规则

| 触发场景 | 更新动作 | 责任人 |
|----------|----------|--------|
| **代码变更** | 同步更新对应文档 | 开发者 |
| **重构完成** | `planned/` → 删除，更新正式文档 | 开发者 |
| **新功能上线** | 从代码生成文档，同步 `public/` | 开发者 |
| **发现文档错误** | 先验证代码，再修正文档 | 发现者 |
| **设计变更** | 更新 `planned/`，添加 ADR | 产品/开发 |

### 更新流程

```
代码变更 → 识别影响的文档 → 更新文档 → 提交（代码+文档一起）
```

## 2.5 废弃与归档策略

### 何时废弃

| 场景 | 处理方式 |
|------|----------|
| 功能已下线 | 文档移到 `archive/` |
| 设计已废弃 | ADR 标记为 `deprecated`，保留原因 |
| 内容已合并 | 删除原文档，保留重定向说明 |
| 临时文档完成使命 | 直接删除 |

### 归档结构

```
archive/
├── audits/              # 审计报告
│   └── YYYYMMDD-xxx.md
├── deprecated/          # 废弃的设计文档
│   └── xxx-design.md
└── README.md            # 归档说明
```

### 归档规则

- 归档文件保留 **90 天**，之后可删除
- ADR 永久保留（即使 deprecated）
- 审计报告保留 **30 天**

## 2.6 文档优先级

### 核心文档（必须维护）

| 类别 | 文档 | 原因 |
|------|------|------|
| 项目入口 | `project/README.md` | AI 和新人首先阅读 |
| 业务规则 | `business/tier-system/*.md` | 影响核心功能 |
| 业务规则 | `business/entitlement/*.md` | 影响核心功能 |
| API 契约 | `engineering/api/*.md` | 前后端协作依赖 |
| 架构决策 | `architecture/decisions/*.md` | 理解系统设计 |

### 扩展文档（按需维护）

# Part 3: 操作规范

> **核心问题**：如何执行文档管理？

---

## 3.1 命名规范

### 文件命名

| 类型 | 格式 | 示例 |
|------|------|------|
| 功能文档 | `{feature}.md` | `editor.md`, `billing.md` |
| 架构文档 | `architecture.md` | `architecture.md` |
| ADR | `{序号}-{标题}.md` | `0001-use-ddd-architecture.md` |
| 临时文档 | `{YYYYMMDD}-{描述}.md` | `20260205-audit-report.md` |

### 命名规则

1. **使用小写英文** + 连字符
   - ✅ `billing-lifecycle.md`
   - ❌ `BillingLifecycle.md`, `billing_lifecycle.md`

2. **避免过长名称**（最多 3-4 个单词）
   - ✅ `permission-matrix.md`
   - ❌ `user-tier-permission-matrix-with-quotas.md`

3. **使用有意义的名称**
   - ✅ `credits-system.md`
   - ❌ `doc1.md`, `new-file.md`

### 目录命名

| 格式 | 示例 |
|------|------|
| `{序号}-{名称}/` | `01-project/`, `05-business/` |
| `{模块名}/` | `billing/`, `auth/` |

---

## 3.2 README 角色

### 每个目录必须有 README.md

**README 应包含**：

```markdown
# {目录名称}

> {一句话描述这个目录的内容}

---

## 本目录包含

| 文档 | 说明 | 状态 |
|------|------|------|
| [xxx.md](./xxx.md) | 描述 | 🟢 |
| [yyy.md](./yyy.md) | 描述 | 🟡 |

## 相关目录

- [相关目录1](../xxx/)
- [相关目录2](../yyy/)

## 收录原则

什么内容应该放在这个目录？什么不应该？
```

### README 不应包含

- ❌ 具体的业务规则（应该在独立文档）
- ❌ 大段的技术说明（应该在独立文档）
- ❌ 与目录内容无关的信息

---

## 3.3 前后端同步流程

### 同步策略

| 文档类型 | 同步策略 | 示例 |
|----------|----------|------|
| **共享业务规则** | 两边完全一致 | `business/tier-system/` |
| **共享设计规范** | 两边完全一致 | `design/tokens/` |
| **后端专属** | 仅在后端 | `engineering/modules/billing/repository.md` |
| **前端专属** | 仅在前端 | `engineering/modules/editor/canvas.md` |
| **重构规划** | 两边同步 | `business/.../planned/` |

### 同步检查清单

修改 `[fullstack]` 文档时：

- [ ] 后端仓库已更新
- [ ] 前端仓库已更新
- [ ] 两边内容完全一致
- [ ] 同时提交两边的 commit

## 3.4 tmp/ 临时目录规范

### 目录结构

```
tmp/
├── working/                 # 进行中的分析
│   └── {YYYYMMDD}-{描述}.md
│
├── to-sync/                 # 待同步到正式文档
│   └── {序号}-sync-to-{目标文档}.md
│
└── disposable/              # 用完即删
    └── ...
```

### 使用规则

| 子目录 | 用途 | 命名规范 | 清理规则 |
|--------|------|----------|----------|
| `working/` | 分析过程、临时规划 | `{YYYYMMDD}-{描述}.md` | 完成后 → `to-sync/` 或删除 |
| `to-sync/` | 结论待同步到正式文档 | `{序号}-sync-to-{目标}.md` | 同步后立即删除 |
| `disposable/` | 临时笔记、调试记录 | 无要求 | 用完立即删除 |
