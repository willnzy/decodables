## 一、核心原则

### 1.1 内容来源优先级

```
┌─────────────────────────────────────────────────────────────────────┐
│                     内容来源优先级（从高到低）                         │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  1️⃣ 代码实际状态（Code as Single Source of Truth）                  │
│     - 从代码结构、逻辑、注释中提取                                    │
│     - 这是唯一的事实来源                                             │
│                                                                     │
│  2️⃣ v1/v2 文档（参考验证）                                          │
│     - 与代码对照后，一致的内容可采用                                  │
│     - 不一致时以代码为准，标注差异                                    │
│                                                                     │
│  3️⃣ 业务规则确认（人工确认）                                         │
│     - 代码和文档都无法确定时，需要人工确认                            │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### 1.2 文档与代码的关系

- **文档反映代码**：v3 文档的目标是准确反映代码的当前状态
- **代码为准**：当文档与代码不一致时，以代码为准
- **规划与实现分离**：未实现的设计放在 `planned/`，已实现的放在 `current/` 或直接目录

## 二、内容分类及处理规则

| 类型 | 识别特征 | 处理规则 | 存放位置 |
|------|----------|----------|----------|
| **A. 当前实现** | 代码中已实现的功能/逻辑 | 从代码提取，写入正式文档 | `internal/` 对应目录 |
| **B. 已验证规则** | v1/v2 内容与代码一致 | 采用文档内容，标注"已验证" | `internal/` 对应目录 |
| **C. 文档过时** | v1/v2 内容与代码不符 | 以代码为准，记录差异原因 | `internal/` + 差异说明 |
| **D. 代码未实现** | v1/v2 有设计但代码未实现 | 归类为"待实现"规划 | `internal/.../planned/` |
| **E. 方案分析** | 曾经的技术选型对比 | 保留到 ADR（决策记录） | `internal/04-engineering/architecture/decisions/` |
| **F. 重构规划** | 未来要做的重构设计 | 保留完整设计 | `internal/.../planned/` |
| **G. 已完成任务** | 审计报告、执行计划等 | 归档或删除 | `archive/` 或删除 |
| **H. 临时内容** | 分析过程、临时笔记 | 用完删除或同步后删除 | `tmp/` |

## 三、内容生成流程

```
┌─────────────────────────────────────────────────────────────────────┐
│                     文档内容生成流程                                  │
└─────────────────────────────────────────────────────────────────────┘

Step 1: 分析代码
    │
    ├── 提取代码结构（目录、文件、类、函数）
    ├── 提取业务逻辑（规则、流程、边界条件）
    ├── 提取数据模型（数据库表、字段、关系）
    └── 提取 API 定义（接口、参数、响应）
    │
    ▼
Step 2: 对照 v1/v2 文档
    │
    ├── 匹配：确认内容正确 → 标注"已验证"
    ├── 不匹配：以代码为准 → 记录差异
    ├── 代码无，文档有：标注"待实现" → planned/
    └── 代码有，文档无：新增文档内容
    │
    ▼
Step 3: 生成 v3 文档
    │
    ├── 当前实现 → internal/.../current/ 或直接 internal/
    ├── 待实现规划 → internal/.../planned/
    ├── 决策记录 → internal/04-engineering/architecture/decisions/
    └── 归档内容 → archive/
```

### 3.1 代码分析要点

**后端代码**：
- `domains/` - 领域模型、业务规则
- `application/` - 用例、服务编排
- `api/routers/` - API 接口定义
- `migrations/` - 数据库结构

**前端代码**：
- `@business/stores/` - 状态管理、业务逻辑
- `@business/services/` - API 调用
- `app/` - 页面结构、路由
- `@core/components/` - 核心组件

## 四、内容更新规则

| 触发场景 | 更新动作 | 责任人 |
|----------|----------|--------|
| **代码变更** | 同步更新对应文档 | 开发者 |
| **重构完成** | `planned/` → 删除，更新 `current/` | 开发者 |
| **新功能上线** | 从代码生成文档，同步 `public/` | 开发者 |
| **发现文档错误** | 先验证代码，再修正文档 | 发现者 |
| **设计变更** | 更新 `planned/`，添加 ADR | 产品/开发 |

### 4.1 更新流程

```
代码变更 → 识别影响的文档 → 更新文档 → 提交（代码+文档一起）
```

### 4.2 文档状态标注

在文档元数据中标注状态：

```markdown
> **状态**: 🟢 已验证 | 🟡 待验证 | 🔴 已过时
> **代码对照日期**: 2026-02-05
> **对应代码**: domains/billing/service.py
```

## 五、特殊内容处理

### 5.1 方案分析（ADR - Architecture Decision Record）

**保留条件**：
- ✅ 涉及重大技术选型（数据库、框架、架构模式）
- ✅ 有多个候选方案且做过对比
- ✅ 未来可能需要重新评估

**不保留条件**：
- ❌ 简单的实现细节选择
- ❌ 没有对比分析的单一方案

**ADR 文件格式**：

```markdown
# ADR-{序号}: {决策标题}

> **状态**: 草案 | 已采纳 | 已废弃 | 已替代
> **日期**: YYYY-MM-DD
> **决策者**: xxx

## 背景

为什么需要这个决策？问题是什么？

## 候选方案

| 方案 | 优点 | 缺点 |
|------|------|------|
| A    |      |      |
| B    |      |      |

## 决策

选择了哪个方案？为什么？

## 后果

这个决策带来的影响是什么？

## 相关文档

- [链接]
```

**存放位置**: `internal/04-engineering/architecture/decisions/`

### 5.2 重构规划

**目录结构**：

```
internal/05-business/entitlement/     # 示例：权限系统
├── README.md                         # 概览 + 实现状态总览
├── current/                          # 🟢 已实现（从代码提取）
│   ├── permission-matrix.md
│   ├── tier-config.md
│   └── ...
├── planned/                          # 🟡 规划中（保留设计文档）
│   ├── README.md                     # 重构规划概览 + 优先级
│   ├── design.md                     # 完整设计文档
│   └── scenarios/                    # 各场景设计
│       ├── tier-downgrade.md
│       └── ...
└── decisions/                        # 🔵 决策历史
    └── why-xxx.md
```

**状态标注**：
- `🟢 已实现` - 代码已完成，文档反映当前状态
- `🟡 规划中` - 设计完成，代码待实现
- `🔴 已废弃` - 决定不实现，保留原因记录

### 5.3 过时内容处理

**识别**：代码与文档描述不符

**处理流程**：
1. 判断：是代码错了还是文档过时
2. 如果代码正确：
   - 更新文档以反映代码
   - 在文档中记录变更原因（可选）
3. 如果代码错误：
   - 记录为技术债务
   - 计划修复代码

## 六、tmp/ 临时目录规范

### 6.1 目录结构

```
tmp/
├── working/                 # 进行中的分析
│   └── {YYYYMMDD}-{描述}.md
│
├── to-sync/                 # 待同步到正式文档
│   └── {序号}-sync-to-{目标文档}.md
│
└── disposable/              # 用完即删
    └── ...
```

### 6.2 使用规则

| 子目录 | 用途 | 命名规范 | 清理规则 |
|--------|------|----------|----------|
| `working/` | 分析过程、临时规划 | `{YYYYMMDD}-{描述}.md` | 完成后 → `to-sync/` 或删除 |
| `to-sync/` | 结论待同步到正式文档 | `{序号}-sync-to-{目标}.md` | 同步后立即删除 |
| `disposable/` | 临时笔记、调试记录 | 无要求 | 用完立即删除 |

### 6.3 示例

```
tmp/
├── working/
│   ├── 20260205-entitlement-code-analysis.md
│   └── 20260205-billing-refactor-plan.md
│
├── to-sync/
│   ├── 001-sync-to-tier-system.md
│   └── 002-sync-to-permission-matrix.md
│
└── disposable/
    ├── debug-notes.md
    └── api-test-results.md
```

## 七、前后端文档同步规则

### 7.1 同步策略

| 文档类型 | 同步策略 | 示例 |
|----------|----------|------|
| **共享业务规则** | 两边完全一致 | `05-business/tier-system.md` |

| **前端专属** | 仅在前端 | `04-engineering/modules/editor/canvas.md` |
| **重构规划** | 两边同步 | `05-business/entitlement/planned/` |

### 7.2 同步标注

在文档元数据中标注：

```markdown
> **同步范围**: [fullstack] | [backend] | [frontend]
```

### 7.3 同步检查

修改共享文档时，必须同时更新两边仓库。
